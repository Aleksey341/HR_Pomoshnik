# AGENTS.md

## Назначение
Единые правила AI-агентов для `HR_Pomoshnik`. Проект следует AI Project Standard 1.0 из `Aleksey341/cursor-ai-workspace/_AI_WORKSPACE/AI-Project-Standard` и дополняет его локальными правилами HR-продукта.

## Перед началом работы
- Прочитать `README.md`, `PROJECT.md`, `SECURITY.md`, релевантные файлы в `docs/`, тесты и существующую реализацию.
- Определить затронутый пользовательский сценарий: поиск, сбор источников, Firecrawl, AI-анализ, managed access, frontend или локальный Flask-режим.
- Найти уже существующий код сценария до создания новой реализации.
- Для нетривиального изменения определить критерий готовности: тест, build, smoke-check или проверяемый API-ответ.

## Режимы работы
- `Review` - анализ без изменения кода.
- `Direct` - небольшое локальное изменение.
- `Investigation` - диагностика ошибки или расхождения.
- `TDD-first` - изменение доступа, security-логики, API-контрактов, парсинга или AI-пайплайна.

## Архитектурные границы
Основные поверхности продукта:

`frontend -> HR Помощник gateway -> OpenAI / Firecrawl`

и локальный режим:

`browser -> Flask -> локальные integrations`

Не смешивать без необходимости:
- browser UI;
- managed access;
- backend secrets;
- Firecrawl/OpenAI gateway;
- локальный режим;
- экспорт и presentation.

## Безопасность
- Реальные `OPENAI_API_KEY`, `FIRECRAWL_API_KEY`, токены и секреты не коммитить и не передавать в браузер в managed mode.
- Не логировать открытые персональные коды доступа.
- Не помещать пользовательские исследования, персональные данные кандидатов/сотрудников или клиентские материалы в Git без явной задачи и обезличивания.
- Не ослаблять CORS, access-code validation или серверное хранение секретов ради удобства разработки.
- Изменение схемы managed access требует теста положительного и отрицательного сценария.

## Правила AI-анализа
- Отделять исходный источник от AI-вывода.
- Не представлять сгенерированное предположение как факт из источника.
- Сохранять ссылки/идентификаторы источников там, где результат исследования должен быть проверяемым.
- При неполных данных явно указывать ограничение.

## Проверка изменений
Перед завершением задачи:
1. запустить релевантный unit/integration тест;
2. для frontend/API изменений проверить существующий CI/build;
3. для security/access изменений проверить отказ при неверном коде и отсутствие утечки секретов;
4. для managed gateway убедиться, что browser-код не содержит backend secrets.
